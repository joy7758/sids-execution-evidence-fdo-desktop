# 智能体运行监测、留痕与审阅交付平台 v0.1 产品蓝图

## 1. 产品定义

### 1.1 这个平台是什么

这是一个面向智能体运行场景的内部平台形态产品。它的核心作用不是“上传几个文件”，而是把一次智能体运行从结果发现、状态判断、证据整理、校验确认，到审阅交付，收成一条更顺手、更稳定的使用路径。

它解决的是这样一类问题：

- 运行结果散落在目录里，普通用户不知道该看什么
- 审阅人员不知道这次运行是否证据齐全、是否已经校验
- 技术接入人希望少解释底层文件，多交付可判断结果
- 内部试点需要一个可以拿来演示、试用、收反馈的桌面入口

### 1.2 它不是什么

它不是下面这些东西：

- 不是一个单纯的三文件上传工具
- 不是普通日志查看器
- 不是模型运行控制台
- 不是大而全的治理平台
- 不是完整策略引擎
- 不是公网 SaaS
- 不是采购或营销展示材料

## 2. 目标用户

### 2.1 技术接入人

这类用户负责把现有运行结果接进来，理解产物目录、接入方式、以及后续如何交付给审阅方。他们关心的是：

- 结果目录能否被自动识别
- 证据是否齐全
- 是否还能保留手动修正入口
- 生成审阅包的路径是否稳定

### 2.2 审阅 / 运营人员

这类用户不希望先理解底层技术细节，而是希望先看到：

- 这次运行是什么
- 结果是否完整
- 校验是否通过
- 有没有需要人工处理的异常
- 是否已经可以导出 / 交付审阅包

### 2.3 非技术内部用户

这类用户通常只参与查看、转交、演示或内部试点。他们需要的是：

- 更接近业务语言的界面
- 清楚的状态提示
- 少量必需操作
- 可以直接交付或转发的结果

## 3. 核心客户路径

平台的理想路径应当是：

1. 系统自动发现最近一次智能体运行结果目录
2. 用户进入后先看到这次运行的状态摘要，而不是先看到一堆文件名
3. 平台自动判断证据是否齐全、校验是否具备、是否需要人工处理
4. 用户在确认无误后，一键生成审阅包
5. 用户直接打开、查看、复制路径或用于交付

这条路径的重点不是“让用户学会 bundle / receipt / summary”，而是让平台替用户先完成识别、整理和提示。

## 4. 平台分层

### 4.1 自动接入层

负责发现和导入智能体运行结果。第一阶段以本地运行结果目录为主，后续再考虑更多来源。

### 4.2 运行结果收件箱

负责承接最近一次或最近几次运行结果，让用户不必自己先在 Finder 里找文件。

### 4.3 运行监测层

负责告诉用户这次运行目前是什么状态，重点包括：

- 是否发现了结果
- 是否证据齐全
- 是否存在缺失或冲突
- 是否需要人工复核

### 4.4 证据 / 回执 / 摘要层

这是当前底座层，仍然围绕三件套展开：

- bundle（证据包）
- receipt（校验回执）
- summary（摘要）

这一层负责把运行结果变成可判断、可验证、可阅读的基础产物。

### 4.5 审阅交付层

负责生成 Review Pack，把底层产物整理成更适合审阅、转交、留存的结果。

### 4.6 未来政策检查层

这一层不是现在就做完整规则引擎，而是未来在界面里补充“有哪些检查项、当前完成到了哪一步、还缺什么”的可见性。

## 5. 核心页面

### 5.1 监测首页

首页应展示最重要的信息：

- 最近一次运行是否已发现
- 当前是否齐全
- 是否可生成审阅包
- 是否有需要处理的问题

### 5.2 最近运行列表

列表页用于承接多次运行结果，让用户能快速区分：

- 哪次是最新的
- 哪次已齐全
- 哪次缺回执或摘要
- 哪次已经生成审阅包

### 5.3 运行详情

详情页应聚焦单次运行，展示：

- 运行来源
- 时间
- 证据完整性
- 校验状态
- 附属文件情况
- 警告与需处理项

### 5.4 审阅包结果页

结果页继续承担交付职责，重点展示：

- 审阅包输出位置
- 核心文件
- 附属文件
- 打开文件夹
- 复制路径

### 5.5 高级 / 手动修正入口

这个入口必须保留，但不应成为默认入口。它用于：

- 自动识别不完整时补路径
- 技术人员临时纠正识别结果
- 处理少量非标准目录

### 5.6 未来设置页边界

未来设置页只应承接必要配置，例如来源路径、默认输出位置、显示偏好。它不应用来承接云账号、模型控制或复杂策略管理。

## 6. 运行状态模型

平台对一次运行至少需要维护以下状态字段：

- run id（运行编号）：用于区分一次具体运行
- source（来源）：来自哪个接入点、目录或系统
- time（时间）：运行产生或被发现的时间
- evidence completeness（证据完整性）：三件套和附属文件是否齐全
- verification status（校验状态）：是否已完成校验、是否通过、是否缺校验回执
- review pack status（审阅包状态）：未生成、可生成、已生成、生成失败
- warnings / needs attention（警告 / 需处理）：多候选文件、缺失文件、路径冲突等
- review-needed flag（需人工复核标记）：是否需要人工确认后再继续交付

这个状态模型的目标不是做复杂编排，而是让用户快速判断“现在能不能继续，问题在哪里”。

## 7. 与现有三件套的关系

平台化并不改变当前底层主输出。

当前核心主输出仍然只有三件：

- bundle（证据包）
- receipt（校验回执）
- summary（摘要）

Review Pack 仍然只是建立在这三件套之上的整理 / 渲染层，用于审阅和交付。

这意味着：

- 平台不会把 Review Pack 抬成新的核心主输出
- 平台不会反向改写三件套的边界
- 平台只是把三件套从“技术文件集合”变成“更容易被发现、理解、验证和交付的产品路径”

## 8. 默认体验原则

平台默认体验必须守住以下原则：

- 系统多做，客户少做
- 先给摘要，后给技术细节
- 先自动发现，再手动选择
- 高级模式永远是次级入口
- 普通用户不应该从 bundle / receipt / summary 开始理解产品

换句话说，平台应该先告诉用户“这次运行是什么状态”，再让技术人员在需要时下钻到底层文件。

## 9. 当前状态 vs 目标状态

### 9.1 当前桌面版状态

当前桌面版已经具备：

- macOS 内部版本
- 运行结果目录导入
- 自动识别三件套
- 生成 Review Pack
- 构建和内部交付链路

但它仍然更接近“单流程桌面工具”，而不是完整的平台入口。

### 9.2 目标平台状态

目标平台状态应当是：

- 用户先看到最近运行和状态，而不是先选文件
- 用户能知道这次运行是否齐全、是否通过、是否需要处理
- 审阅包生成是顺手的后续动作，而不是唯一主页面
- 后续还能自然承接政策检查项展示

### 9.3 二者差距

当前与目标之间的主要差距在于：

- 还没有“运行结果收件箱”视角
- 还没有“最近运行列表”视角
- 还没有统一的运行状态卡片
- 还没有清晰的运行详情页
- 还没有把审阅包流程嵌进“监测 → 判断 → 交付”的连续路径里

## 10. 后续阶段图

### M1：运行结果收件箱 + 最近结果自动发现

把“导入目录”进一步收成“最近运行结果自动发现”的默认入口，让用户先看到最近结果。

### M2：运行列表 + 状态卡片

增加运行列表与状态卡片，让用户能同时看多次运行，而不是一次只处理一个目录。

### M3：运行详情 + 证据完整性

把一次运行的证据完整性、回执状态、附属文件、警告信息收进详情页。

### M4：一键审阅包流程优化

继续压缩从运行状态到审阅包结果之间的操作成本，让生成审阅包更像平台默认动作，而不是单独工具动作。

### M5：未来政策检查项展示

在不引入完整策略引擎的前提下，先把政策检查项可见性做出来，让用户知道“平台会看哪些点、当前还缺什么”。

## 11. 明确不做什么

当前阶段明确不做：

- Windows
- 签名 / 公证
- 云端 / 账号 / 同步
- provider-running UI
- 大治理平台
- 完整策略引擎
- 公网 SaaS
- 采购 / 营销话术

这些都不属于当前 v0.1 平台化收口的必要范围。

## 12. 开放问题

当前最重要的开放问题只有这些：

- 最近运行结果的默认发现范围应当是什么：单目录、固定入口，还是用户可配置来源
- 运行列表应按“时间”优先，还是按“待处理程度”优先
- 证据完整性是否只做“齐全 / 不齐全”，还是要补一个更细的分层状态
- 审阅 / 运营人员最先需要看到的是“校验状态”还是“需人工复核”
- 未来政策检查项展示，应先做静态检查清单，还是先做少量可执行检查项

以上问题应基于内部试用反馈来决定，不应在当前阶段靠预设想象一次性定死。
