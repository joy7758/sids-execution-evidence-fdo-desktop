# 客户友好度 + 中文优先 + PDF 交付规范 v0.1

## 1. 产品原则

### 1.1 系统多做，客户少做

这个产品的默认路径不应该建立在“客户先理解底层文件”之上，而应该建立在“系统先识别、先判断、先整理”之上。客户首先看到的应该是这次运行有没有结果、是否完整、能不能继续，而不是一组技术文件名。

### 1.2 中文优先，英文辅助

当前目标客户是中国政企、国企和内网试点场景，因此主界面、主按钮、主状态、主报告都必须以中文为第一语言。英文应当保留，但角色是完整辅助语言，而不是主交付语言。

### 1.3 先状态，后技术细节

默认界面先展示“这次运行现在处于什么状态”，例如是否已识别、证据是否完整、校验是否通过、是否可生成审阅包。技术文件路径、候选文件提醒和底层字段应当放进详情，而不是首页默认展开。

### 1.4 先结果，后文件

客户首先关心的是“有没有结果、结果能不能交付、报告在哪里”，其次才是 `bundle`、`receipt`、`summary` 等底层文件。结果页也应当把正式交付物放在第一层，而不是把文件树放在第一层。

### 1.5 先默认路径，后高级模式

默认路径应当始终是：

- 自动发现最近运行结果
- 自动判断是否完整
- 一键生成审阅包

高级手动模式必须保留，但它只解决识别不完整、目录不标准、技术人员修正路径这类问题，不应成为普通用户的起点。

## 2. 参考产品吸收点

### 2.1 ChatGPT：一个主动作，弱化干扰

首页不应该让客户面对太多入口。应当明确一个最主要动作，例如“使用最近运行结果”或“生成审阅包”，其余内容降为次级入口，避免界面先把用户带进设置、技术细节或文件管理。

### 2.2 LangSmith：先总览，再看运行细节

平台应该先给出一次运行的总体状态，再允许下钻查看识别详情、证据完整性和异常点。也就是说，总览优先，细节次之。

### 2.3 Langfuse / Phoenix：运行列表 + 详情下钻

成熟产品不会把底层文件直接当首页。更好的做法是先按“运行”组织信息，再在运行详情里展开证据、回执、摘要和后续交付动作。

### 2.4 Helicone：轻接入、少让客户理解内部结构

轻接入的重点不是暴露更多内部术语，而是减少客户理解成本。客户不需要先知道系统内部怎么组织文件，只需要知道“这次运行已发现、可查看、可交付”。

## 3. 页面级体验原则

### 3.1 首页

用户第一眼应该看到：

- 最近一次运行是否已找到
- 当前是否可生成审阅包
- 是否存在需要处理的问题

主动作应当是：

- 使用最近运行结果

默认隐藏的内容：

- 具体文件路径
- 多候选文件提醒
- 技术性错误细节

放到详情里的内容：

- 识别出的文件清单
- 附属文件路径
- 更细的异常信息

### 3.2 最近运行列表页

用户第一眼应该看到：

- 最近几次运行
- 哪次是最新的
- 哪次状态正常
- 哪次需要处理

主动作应当是：

- 打开某次运行

默认隐藏的内容：

- 完整文件路径
- 原始技术字段

放到详情里的内容：

- 识别依据
- 具体缺失项
- 校验回执细节

### 3.3 运行详情页

用户第一眼应该看到：

- 运行结果目录
- 证据完整性状态
- 校验状态
- 是否可生成审阅包

主动作应当是：

- 生成审阅包

默认隐藏的内容：

- 原始路径列表
- 候选文件冲突说明

放到详情里的内容：

- `bundle / receipt / summary` 原始路径
- supporting files 明细
- 识别 warning

### 3.4 审阅包结果页

用户第一眼应该看到：

- 审阅包是否生成成功
- 正式交付物在哪里
- 下一步怎么打开或转交

主动作应当是：

- 打开文件夹
- 打开 PDF 报告

默认隐藏的内容：

- 技术中间文件
- 原始 engine 返回细节

放到详情里的内容：

- `index.json`
- Markdown 中间报告
- supporting files 路径

### 3.5 高级模式入口

高级模式应始终是次级入口。它的职责是：

- 在自动识别不完整时修正
- 在目录不标准时补路径
- 给技术人员排查问题

高级模式不应用来承担普通用户的默认主路径。

## 4. 中文优先规则

### 4.1 主界面文案规则

所有主标题、主按钮、状态文案默认使用中文，包括：

- 首页标题
- 状态卡片
- 主动作按钮
- 结果页主结论
- 报告标题

英文应保留为完整辅助语言，但不应反客为主。

### 4.2 底层三件套的显示规则

`bundle / receipt / summary` 仍然是系统底座，但在客户界面里不能作为第一层话术直接出现。

对客户显示时必须优先写成：

- 证据包文件
- 校验回执文件
- 摘要文件

如需保留英文标识，应采用括号辅助形式，而不是让英文短词主导界面。

### 4.3 报告与状态卡片规则

审阅报告、结果页、状态卡片必须中文优先。至少以下内容应默认中文：

- 结论
- 当前状态
- 是否完整
- 是否通过校验
- 是否可交付
- 需处理项

## 5. 报告交付规则

### 5.1 中文版报告作为主版本

审阅报告必须提供中文版作为主版本。英文版如果需要，应视为补充版本，不应作为中国客户交付的默认版本。

### 5.2 PDF 作为正式交付格式

PDF 必须是正式交付格式。它的角色是：

- 可阅读
- 可转交
- 可归档
- 不要求客户理解原始技术文件

### 5.3 Markdown 只是中间格式

Markdown 可以继续保留，但它的定位应当是：

- 技术中间格式
- 调试或内部留痕格式
- 后续渲染 PDF 的输入格式

它不应再被默认视为最终客户交付主格式。

### 5.4 结果页默认突出 PDF

结果页默认应突出：

- PDF 报告
- 保存位置
- 打开文件夹
- 复制路径

而不是先突出 `report.md` 或底层结构文件。

## 6. 下一轮代码改造范围

### 6.1 U1：桌面端 UX 收敛

U1 只处理桌面端客户友好度收敛，重点包括：

- 首页更聚焦一个主动作
- 最近运行列表更易读
- 运行详情先状态、后细节
- 高级模式入口进一步弱化
- 结果页突出正式交付物

### 6.2 R1 / R2：核心中文报告 + PDF 导出

R1 负责把核心审阅报告改成中文优先。

R2 负责把报告正式导出为 PDF，并把 PDF 放到结果页主交付位置。

这两步都不应与更大的平台功能扩张混在一起做。

## 7. 明确不做什么

本规范当前明确不覆盖：

- Windows
- 签名 / 公证
- 云端 / 账号 / 同步
- provider-running UI
- 大治理平台
- 完整策略引擎
- 公网 SaaS
- 市场和采购话术

## 8. 开放问题

当前最值得保留的开放问题只有这些：

- 首页是否只保留一个主动作，还是保留两个同级动作
- 最近运行列表默认展示几条，怎样避免首页信息过重
- 中文报告中哪些技术字段需要保留，哪些应该折叠到附录
- PDF 是只导出主报告，还是把部分关键附属信息一起带进去
- 结果页中 Markdown 是否还需要默认可见，还是完全降为技术详情
