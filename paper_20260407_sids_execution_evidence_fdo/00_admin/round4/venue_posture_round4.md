# Venue Posture Round 4

## 这篇稿子在 SIDS 里靠什么赢

- 靠一个清楚、可检查、可复现的窄工件闭环。
- 靠把 `single-operation accountability` 讲成 data-space / FDO 语境下的具体验证问题，而不是抽象治理口号。
- 靠 `profile + schema + validator + examples + tests + walkthrough` 的 closure。
- 靠工程边界清楚，评审容易判断“它到底做成了什么”。

## 这篇稿子不是靠什么赢

- 不是靠规模。
- 不是靠 broad scope。
- 不是靠 portability。
- 不是靠 full FDO interoperability。
- 不是靠平台化叙事。
- 不是靠大段 related work 或概念宣言。

## 为什么 `closure > scope`

- 当前 repo-backed 事实面本来就小，扩大 scope 只会制造不被证据支持的脆弱句子。
- workshop 稿的赢面来自“可被迅速判断的扎实结果”，不是“想做很多事情”。
- 一条可运行、可验证、可独立复查的边界，比多个半成立的广泛主张更适合当前稿面。
- 在 6 页压力下，scope 越大，越容易把正文写成防御性否定清单。

## 为什么这篇应该看起来像 bounded engineering paper，而不是 manifesto

- 本文贡献不是提出一个新生态，也不是重写 data spaces 的治理语言。
- 本文真正提供的是一个 operation-centered object 和一条可执行 validation path。
- 评审要看到的是可检查的 engineering surface，而不是抽象口号。
- 只要稿子像 manifesto，评审就会自然追问平台、互操作、部署与规模；这些都不是当前 artifact 能支撑的赢法。
