Agent-mediated operations are becoming a practical part of FDO and data-space settings. Objects may be read, transformed, enriched, or re-emitted under explicit policy conditions, yet the external review surface for those actions often remains weak. System operators may have traces, logs, and internal runtime records, but an outside reviewer still faces a harder question: can one concrete operation be inspected later as a bounded and independently checkable object?

This paper addresses that question at a deliberately small scale. We do not start from a larger system surface, a registry design, or a broad interoperability layer. We start from one operation. The core problem is not that current systems fail to record events. The problem is that the recorded material is usually not organized as a compact accountability object for one action. A trace may help an engineer debug a run, but it may still leave a reviewer to reconstruct who acted, on which object, under which policy, through which evidence links, and by what validation path.

That distinction matters in FDO and data-space settings because operations are object-centered. A reviewer may need to know not only that an agent produced runtime output, but also that one subject object was acted on, that the governing policy and constraints were explicit, that input and output references closed correctly, and that the resulting evidence object remained internally consistent. These are accountability questions rather than observability questions. They require a representation that is small enough to inspect directly and precise enough to validate automatically.

We therefore frame execution evidence not as richer logging, but as a checkable accountability object for one operation. The object is intentionally narrow. It is not a full provenance family, not a general trust infrastructure, and not a broad governance layer. Instead, it is a minimal profile for one operation accountability statement. Its role is to capture the smallest set of fields and relations needed to make one operation inspectable in a stable way. In the current artifact, those fields are organized around an operation-centered design with supporting context for the actor, subject, policy, constraints, provenance, evidence, and validation path.

The motivation for a minimal profile is practical as well as conceptual. A large model with unconstrained extension points would weaken the very property this paper tries to establish: bounded independent checking. The current profile is therefore designed as a closed, reviewable object with explicit top-level sections and explicit link rules. The profile is paired with a JSON Schema and a profile-aware validator so that the accountability statement is not merely declared but exercised. The validator checks four bounded properties of the shipped artifact: schema conformance, reference closure, cross-field consistency, and minimal integrity recomputation. Together, these checks define the current verification boundary.

This validator-aware path is central to the paper. The contribution is not a passive schema that others might interpret differently. The contribution is a small executable closure: a profile, a schema, a validator, controlled examples, and a runnable demo. In the current repo-backed baseline, the example boundary is intentionally small. There is one valid example and three controlled invalid examples, each aligned with one main failure class. The valid example shows the passing path for one operation accountability statement. The invalid examples expose a missing required field, an unclosed reference, and a broken evidence-policy link. The demo follows the same narrow design choice by showing one metadata-enrichment walkthrough rather than a family of scenarios.

This narrowness is not a hidden limitation disguised as a feature; it is the methodological choice that makes the artifact legible. A broader scope would immediately invite claims about cross-setting validity, deployment, or multi-agent coverage that the current implementation does not support. By keeping the boundary to one repo-backed valid context and three controlled invalid examples, the paper can make a more defensible claim: one operation in an FDO-based setting can be expressed as a bounded accountability object and checked through a concrete validation path.

The present paper therefore makes a small engineering contribution with a clear review surface. It contributes a minimal execution-evidence profile for one operation accountability statement, a schema and validator path that make that statement checkable, and a shipped artifact closure consisting of one valid example, three invalid examples, test anchors, and one single-path metadata-enrichment demo. It does not claim validated transfer across additional runtimes or settings, deployment evidence, full FDO interoperability, or broader governance coverage. Its value lies in closure rather than breadth: not richer traces, but a checkable accountability object for one operation.
