FDO and data-space settings increasingly rely on object-mediated operations carried out by software agents. An agent may read an object, update metadata, emit derived references, and do so under explicit policy conditions. Later review, however, is often weaker than execution itself. A runtime may expose traces and logs, yet an external reviewer still has to reconstruct what was acted on, under which rule surface, and whether the resulting record is internally coherent. The digital-object lineage explains why this matters: object identity and machine-handled interaction are central at the systems level, but they do not by themselves supply a compact accountability object for one operation [@kahn2006framework; @dona2018doip; @soilandreyes2024evaluating].

That gap is narrower than observability. A trace is useful for debugging, but debugging and later accountability are not the same review task. A reviewer-facing record has to state the actor, subject, operation, policy surface, evidence links, and validation state for one operation in a form that can be checked directly. It also has to make those relations explicit enough that a third party can test them without reconstructing the full runtime. When those relations remain implicit or scattered across runtime records, later review depends on reconstruction rather than inspection.

This paper takes the smallest path we can defend. It treats execution evidence as a single-operation accountability object with an explicit profile, not as a larger telemetry stack. The shipped artifact couples that profile to a JSON Schema and a validator that checks four properties: schema conformance, reference closure, cross-field consistency, and bounded integrity recomputation. The point is not richer logging. The point is a small object that another party can load, validate, and interpret without replaying a larger runtime. In that sense, the paper is closer to provenance validity work than to larger interoperability proposals [@moreau2013provdm; @cheney2013provconstraints].

The current repo-backed surface is deliberately tight: one valid example, three controlled invalid examples, tests, a command-line validation path, and one runnable walkthrough over a metadata update operation. That boundary is also the paper's scope boundary. The paper claims that this one context can be represented and checked as a bounded accountability object. It does not claim more than the artifact shows. This is important for reviewability: a narrow claim can be matched directly against the shipped validation path, while a wider claim would immediately outrun the available evidence.

Within that boundary, the contribution is practical. First, the paper defines a minimal operation-centered profile with explicit top-level relations for actor, subject, operation, policy, constraints, provenance, evidence, and validation. Second, it provides a validator path that turns the profile from a descriptive format into an executable check surface. Third, it documents a small artifact closure in which one positive case, three negative cases, tests, and one walkthrough can be inspected together. The result is not simply a data format. It is a small reviewable package in which the object model, validation rules, and exercise path stay aligned. For a short workshop paper, that closure matters more than breadth: it gives reviewers a concrete engineering object to evaluate.
