The method is an operation-centered object model plus a bounded validation path. The object model is encoded as one JSON record whose top-level sections are `profile`, `statement_id`, `timestamp`, `actor`, `subject`, `operation`, `policy`, `constraints`, `provenance`, `evidence`, and `validation`. These sections are not independent metadata buckets. They form one relation layer around a single operation statement, and that shared relation layer is what later validation works on.

Each section has a bounded role. `profile` fixes identity and version. `statement_id` and `timestamp` identify one statement instance. `actor` records who performed the operation. `subject` records the primary object acted on. `operation` records the action and its input and output references. `policy` and `constraints` record the governing rule surface. `provenance` ties actor, subject, operation, and input or output references together. `evidence` records emitted references, artifacts, and integrity fields. `validation` records how the statement is to be checked.

The design keeps the operation at the center. That choice is structural, not rhetorical. The operation links outward to subject, inputs, outputs, and policy. Provenance repeats those references so that they can be checked rather than inferred. Evidence binds the statement to emitted references and artifacts. Validation binds the statement to the objects and checks used to review it later. This arrangement supports one bounded question: whether a later reader can inspect one statement and determine that its internal relation layer is coherent. It therefore turns accountability into a checkable object question rather than a runtime reconstruction task.

The shipped JSON Schema provides the structural contract for this object. At that layer, the method enforces required fields, fixed profile identifiers, value types, formats, and bounded enums. Schema checks are therefore the first gate. A malformed instance does not enter later stages. This separation matters because it keeps field shape distinct from deeper relation checking. It also keeps later diagnostics interpretable: once schema shape passes, later failures can be read as relation failures rather than syntax failures.

The reference validator then applies four stages. Stage one checks schema conformance. Stage two checks reference closure: local identifiers for the subject, policy, constraints, inputs, outputs, evidence items, and validation targets must resolve where the profile expects them. Stage three checks cross-field consistency: input and output references must align with their declared roles, provenance input and output lists must agree with the operation section, and policy linkage must remain consistent across the operation, evidence, and validation sections. Stage four performs bounded integrity recomputation. It recomputes digests over the reference list, artifact list, and statement core, and then checks whether the stored integrity fields match those recomputed values. Taken together, these four stages give the artifact a stable failure grammar: malformed structure, broken references, inconsistent relations, or mismatched integrity fields.

This validation path is intentionally small. It does not attempt to prove everything that could matter in a larger runtime. It checks whether the shipped object satisfies the bounded rules that the current profile declares. That is what makes the result reviewable: each validation stage corresponds to a specific class of failure that a reviewer can inspect. The method therefore favors explicit rule surfaces over open-ended interpretation.

The current implementation exposes the same path through a reference CLI. The CLI reads one profile instance and returns a machine-readable JSON report. On success, the report indicates a clean pass with no issues. On failure, it records stage-specific issues and exits non-zero. This behavior is part of the method rather than an afterthought, because it is what makes the profile independently exercisable. A reviewer does not need private harness code to reproduce the basic pass or fail outcome.

The shipped examples, tests, and runnable walkthrough all exercise this same path. One valid case serves as the positive witness. Three invalid cases each break one primary rule class: required-field completeness, reference closure, or the evidence-to-policy relation. The walkthrough shows that the same validation path can be rerun on a single end-to-end case rather than only on static files. Together these pieces define the current method boundary and keep the object model, rule surface, and exercise surface tied to the same artifact.
